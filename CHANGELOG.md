# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the version is `0.x`, minor releases may contain breaking changes; every one is listed under **Breaking**.

## [0.1.0] - Unreleased

### Breaking

- The module now requires Go 1.26.9 (`go 1.26.9` in `go.mod`).
- `ValidateHost` now accepts only RFC 3986 host characters (letters, digits, `-._~%!$&'()*+,;=`, `:` and `[` `]`). Hosts containing spaces, control bytes, `@`, `/`, `\`, `?`, `#`, quotes or non-ASCII bytes are rejected, both for HTTP/2 `:authority` and on the HTTP-to-HTTPS redirect listener.
- HTTP/1 requests are parsed strictly (RFC 9110/9112). The following are answered with `400 Bad Request` and the connection is closed: a header name that is not a token (including whitespace before the colon); a control byte, DEL, lone CR or bare LF anywhere in the request line or a header line; an obsolete line fold; a header line without a colon or with an empty name; an HTTP/1.1 request without a `Host` header; more than one `Host` header; a `Host` value that fails `ValidateHost`; an empty request target. Header values now have leading and trailing whitespace removed (previously only one leading space). An absolute-form target (`GET http://host/path`) sets `Request.Host` from the target.
- `RealIP(...)` and `New(Config{TrustedProxies: ...})` panic on an entry that is neither an IP address nor a CIDR. Previously the entry was ignored, and `RealIP` with no valid entry trusted forwarding headers from every peer.
- The response cache (`Cache`, `NewResponseCache`) no longer stores or serves requests that carry `Authorization` or `Cookie`, unless `CacheConfig.KeyFunc` is set. Responses with a `Vary` header naming anything other than `Accept-Encoding` are not stored.
- The reverse proxy no longer retries a request on another backend after the request was sent, unless the method is `GET`, `HEAD`, `OPTIONS` or `TRACE` or the request carries `Idempotency-Key` / `X-Idempotency-Key`. Failures before anything was sent (refused connection, DNS, connect timeout) are still retried for every method. A backend timeout is now answered with `504 Gateway Timeout` instead of `502`.
- `FileHeader.Data` shares memory with the request body and is valid only until the handler returns, the same rule as `Request.Body`. Copy it to keep it longer. A malformed multipart body now yields no form values or files instead of a partial result. Upload file names are sanitised (directory components, control bytes, `.` and `..` removed; capped at 255 bytes).
- Router method handling follows RFC 9110. A `HEAD` request to a path that has only a `GET` route runs the `GET` handler (the body is not sent); previously it got `405`. An `OPTIONS` request to a path with no `OPTIONS` route gets `204 No Content` with an `Allow` header; previously `405`. Every `405` carries `Allow` listing the methods registered for the path in alphabetical order, with `HEAD` included when `GET` exists and `OPTIONS` always included; a custom `MethodNotAllowed` handler receives the response with `Allow` already set. Methods are matched exactly: `Router.Lookup` previously routed any method whose first two letters matched a known method (`GETX` ran the `GET` handler); unknown methods now get `404`.
- An HTTP/1 request with an `Expect` value other than `100-continue` is answered with `417 Expectation Failed` and the connection is closed.
- Malformed chunked trailer fields (bad name, control bytes, no colon) are rejected instead of skipped.
- An HTTP/2 request whose DATA frames do not add up to its `content-length` is reset with `PROTOCOL_ERROR` (RFC 9113 §8.1.1), as is a `HEADERS` frame that ends the stream while declaring a non-zero length. Two `content-length` fields with different values are a malformed request.
- Responses with status `304` no longer carry `Content-Length: 0`.
- `Static` serves files of any size by streaming them; the `413` for files over 64 MiB is gone.
- HTTP/3: every new client address is validated with a QUIC Retry before any connection state is created (RFC 9000 §8.1.2). A client's first connection therefore takes one extra round trip; later connections that present the `NEW_TOKEN` the server sent skip it.
- A TLS client that offers ALPN protocols but none the server supports (`h2` when HTTP/2 is enabled, `http/1.1`) now fails the handshake with a `no_application_protocol` alert (RFC 7301 §3.2). Previously the connection continued without ALPN and was served as HTTP/1.1. Likewise, a QUIC client that does not offer `h3` is refused with `CRYPTO_ERROR` `0x178` (RFC 9001 §8.1).
- `BuildServerHello` takes the key-exchange group as a new fourth argument: `BuildServerHello(random, sessionID, suiteID, group, pubKey)`.
- `CSRF` also checks where an unsafe request (anything but `GET`, `HEAD`, `OPTIONS`, `TRACE`) comes from, before the token check, and answers `403` (or calls `ErrorHandler`) when: `Sec-Fetch-Site` is `cross-site`; `Sec-Fetch-Site` is `same-site` and the `Origin` is not in `CSRFConfig.TrustedOrigins`; an `Origin` is present that is neither the request's own origin nor trusted (`Origin: null` included); or, over HTTPS with no `Origin`, a `Referer` from another origin is present. Requests without these headers (most non-browser clients) go straight to the token check, which is unchanged. The request's own scheme is `https` for TLS connections, and also when the connection comes from a trusted proxy (`Config.TrustedProxies`, `Config.ProxyMode` or `RealIP`) that sends `X-Forwarded-Proto: https`. Behind a TLS-terminating proxy that is not configured as trusted, browser requests carry an `https://` origin while the server sees plain HTTP, and are rejected: configure the proxy as trusted or list the site's own origin in `TrustedOrigins`.
- `DefaultSecurityHeaders()` now includes `Cross-Origin-Opener-Policy: same-origin`. A page served with it loses its `window.opener` link to cross-origin popups, which breaks login or payment flows that open a provider's window and wait for it to call back through `window.opener`; set `CrossOriginOpenerPolicy` to `same-origin-allow-popups` (or `""` to omit the header) for those pages.
- Log output changed format. The server logs through `log/slog` (see `Config.Logger`); the default output is `[INFO] certificate added domain=example.com` rather than free-form text, and the `Logger()` middleware writes `[INFO] request proto=HTTP/1.1 method=GET path=/ status=200 elapsed=…`. Programs that parse the old log lines need updating. A recovered panic is logged as `[ERROR] recovered panic panic=… stack=… method=… path=…` instead of `[PANIC] …`; handler panics on the epoll server's HTTP/1 and HTTP/2 paths used to be answered with `500` without being logged at all.
- `JWT(...)` panics when the config has no `Secret`, `Key` or `KeyFunc`; it used to verify signatures against an empty HMAC key, which anyone can sign with. Tokens are now also rejected when `nbf` or `iat` lies in the future (beyond `JWTConfig.Leeway`), when `exp`, `nbf` or `iat` is not a number, when the header carries `crit`, and when any part uses padded or non-canonical base64url. A token whose `exp` equals the current second is expired (RFC 7519 §4.1.4).

### Added

- MIT license (`LICENSE`), security policy (`SECURITY.md`) and this changelog.
- `core.Version` constant.
- GitHub Actions CI: vet, staticcheck (linux/windows/darwin matrix), race tests, fuzzing, govulncheck, benchmark smoke run.
- Fuzz targets for every wire parser (HTTP/1 head, chunked bodies, HPACK, QPACK, QUIC frames/headers/transport parameters/packet decryption, TLS ClientHello/ClientKeyExchange/record decryption, WebSocket frames, cookies, query strings, multipart, JWT, request paths, hosts, Accept-Encoding), plus differential fuzzing of every SIMD/SWAR scanner against a byte-by-byte reference.
- `CacheConfig.KeyFunc func(*Request) (string, bool)`: replaces the default cache key and the `Authorization`/`Cookie` bypass; returning `false` skips the cache.
- `Stats.H1Rejected`: count of HTTP/1 requests rejected by the strict parser.
- `FileHeader.Header` (all part headers) and `FileHeader.Open()`.
- Multipart parsing follows RFC 7578: unquoted and quoted parameters, case-insensitive parameter names, `filename*=UTF-8''…` (RFC 8187), a delimiter is recognised only at the start of the body or after CRLF, part header blocks are capped at 8 KiB.
- `Request.Context()` is cancelled when the client goes away and when `Shutdown`'s context expires, on the epoll backend: an HTTP/1 client closing or half-closing the connection, an HTTP/2 `RST_STREAM` for the request's stream, or the connection closing. `Request.CancelCause()` reports `ErrClientGone` or `ErrServerShutdown`. The context is created only when a handler calls `Context()`, so requests that never call it pay nothing.
- `100 Continue` is sent automatically, once, for `Expect: 100-continue` when the server starts reading the request body. A request whose declared body exceeds the size limit gets `413` without it, a request with no body never gets it, and the header is ignored on HTTP/1.0.
- Request trailers: `Request.Trailers()` returns the trailer fields of a chunked HTTP/1 body or an HTTP/2 request. Fields that are not allowed in trailers (`Host`, `Content-Length`, `Transfer-Encoding`, `Trailer`, `Connection` and other connection-specific fields) are rejected.
- Range and conditional requests for `SendFile` and `Static`: `ETag` (`"<mtime-ns hex>-<size hex>"`), `Last-Modified` and `Accept-Ranges: bytes` on every file response; `If-Match`, `If-Unmodified-Since`, `If-None-Match` and `If-Modified-Since` evaluated in RFC 9110 §13.2.2 order (`304`/`412`); a single byte range answered with `206` and `Content-Range`, an unsatisfiable range with `416` and `Content-Range: bytes */<size>`; `If-Range` with a strong ETag or the exact `Last-Modified` date. Multiple ranges, invalid ranges and ranges on methods other than `GET` are ignored and the full file is sent. Range responses use `sendfile(2)` from the requested offset where the zero-copy path applies.
- `412 Precondition Failed` reason phrase.
- HTTP/3 graceful shutdown. `Shutdown` sends `GOAWAY` on every HTTP/3 connection with the first client request stream it has not processed; requests on lower streams finish normally, later ones are refused with `RESET_STREAM`/`STOP_SENDING` `H3_REQUEST_REJECTED`, and the connection is closed with `H3_NO_ERROR` once its requests are answered and acknowledged. If `Shutdown`'s context expires first, running handlers are cancelled with `ErrServerShutdown` and the connections are closed.
- `Alt-Svc: h3=":<port>"; ma=86400` is added to HTTPS responses (HTTP/1.1 and HTTP/2, including streamed responses) once `ListenAndServeQUIC` has bound its UDP port. It is never sent over plain HTTP or h2c, nor when the handler set its own `Alt-Svc`. `Config.DisableAltSvc` turns it off.
- QUIC address validation: Retry packets with the RFC 9001 §5.8 integrity tag, and `NEW_TOKEN` after the handshake and after each successful path validation. Tokens are AES-GCM sealed; a Retry token is valid for 10 seconds from the same IP address and port, a `NEW_TOKEN` for 24 hours from the same IP address. Keys rotate every 24 hours and the previous key is still accepted. A forged, expired or mismatched Retry token closes the attempt with `INVALID_TOKEN`.
- QUIC connection migration (RFC 9000 §9): a non-probing packet from a new address moves the connection there at once, with the 3× anti-amplification limit until `PATH_CHALLENGE`/`PATH_RESPONSE` validates the path, a fresh peer connection ID when the client has supplied one, and a congestion-controller reset on validation. If validation fails, the connection returns to the last validated address. `PATH_CHALLENGE` is answered on the path it arrived on.
- QUIC connection IDs: after the handshake the server issues up to three more connection IDs (bounded by the client's `active_connection_id_limit`), replaces any the client retires, and honours the client's `NEW_CONNECTION_ID` and `retire_prior_to`.
- QUIC stateless reset (RFC 9000 §10.3): packets for unknown connections get a stateless reset at most 64 bytes long and always shorter than the packet that triggered it, rate-limited to 100 per second per server. The token is advertised in the `stateless_reset_token` transport parameter. `Config.QUICStatelessResetKey` keeps tokens valid across restarts; without it a random key is generated at start-up.
- QUIC `RESET_STREAM` and `STOP_SENDING`: a peer reset cancels the running handler with `ErrClientGone` and abandons a request that was not complete; `STOP_SENDING` resets the response stream. Final sizes and flow-control limits are checked on reset.
- HTTP/3 control and QPACK streams from the client are read and checked (RFC 9114 §6.2 and §7.2, RFC 9204 §4.2): `SETTINGS` must come first and only once, reserved HTTP/2 settings and frame types are rejected, duplicate critical streams and push streams are refused, closing a critical stream is an error, and unknown stream types are stopped with `H3_STREAM_CREATION_ERROR`.
- `Config.QUICStatelessResetKey []byte` and `Config.DisableAltSvc bool`.
- TLS alerts (RFC 8446 §6, RFC 5246 §7.2). A failed handshake or a bad record on the epoll TLS server is now reported to the client before the connection closes, instead of a bare close: `decode_error` for a malformed ClientHello or Finished, `protocol_version` for a client that offers nothing newer than TLS 1.1, `no_application_protocol`, `unrecognized_name` when neither a certificate for the requested name nor a default certificate exists, `handshake_failure` when no cipher suite, group or signature scheme is shared, `illegal_parameter` for an invalid key share, `bad_record_mac` for a record that fails to decrypt, `decrypt_error` for a wrong Finished, `record_overflow` for an oversized record, `unexpected_message` for a record or message out of order, and `internal_error` for server-side failures. Alerts are plaintext until the server has switched keys and encrypted afterwards. A first record that is not TLS (for example plain HTTP sent to the TLS port) and alerts sent by the client still close without a reply. On QUIC the same conditions close the connection with `CRYPTO_ERROR` `0x0100` + alert (RFC 9001 §4.8), sent in Handshake packets once those keys exist and in Initial packets before.
- TLS 1.3 key exchange over P-256 and the hybrid post-quantum group X25519MLKEM768 (`0x11EC`: ML-KEM-768 from `crypto/mlkem` combined with X25519), in addition to X25519, on the epoll TLS server and on QUIC. Among the key shares a client sends, the server picks X25519, then X25519MLKEM768, then P-256; `Config.TLSPreferPostQuantum` (default `false`) puts X25519MLKEM768 first. A client that sent only an X25519MLKEM768 or P-256 share previously failed the handshake. An invalid share (wrong length, a point not on the curve, an X25519 point of low order, an ML-KEM key out of range) gets `illegal_parameter`.
- HelloRetryRequest (RFC 8446 §4.1.4). When none of the client's key shares is usable but its `supported_groups` lists a group the server supports, the server asks for a share in that group instead of failing. The second ClientHello must carry exactly one share, for the requested group, and must otherwise match the first (version, random, session ID, cipher suites, groups, signature schemes, server name, ALPN); anything else gets `illegal_parameter`. At most one retry is sent. Over TCP a single compatibility `change_cipher_spec` follows the HelloRetryRequest and none follows the ServerHello; over QUIC there is none.
- `Config.TLSPreferPostQuantum bool`.
- TLS 1.3 session resumption (RFC 8446 §2.2, §4.6.1). After a full handshake the server sends one `NewSessionTicket`; a returning client that presents it in `pre_shared_key` (with `psk_dhe_ke`) skips the certificate and its signature while still doing a fresh key exchange. Tickets are stateless: the session is sealed with AES-256-GCM under a server key that rotates every 24 hours, and tickets under the previous key are still accepted. A ticket is used only for the server name it was issued for and a cipher suite with the same hash; anything else falls back to a full handshake. A wrong PSK binder gets `decrypt_error`; a `pre_shared_key` that is not the last extension, or whose identity and binder counts differ, gets `illegal_parameter`. 0-RTT early data is never accepted. Tickets are issued only to clients that offered `psk_dhe_ke`. HTTP/3 connections resume the same way: the ticket arrives in a 1-RTT `CRYPTO` frame after the handshake, and only tickets issued for `h3` are accepted over QUIC.
- TLS 1.2 session tickets (RFC 5077). A client that offers the `session_ticket` extension receives a ticket before the server's Finished; presenting it later gives an abbreviated handshake with no certificate and no key exchange, and the ticket is renewed each time. The same sealed format, keys, lifetime and server-name rule as TLS 1.3 apply, the ticket's cipher suite must be offered again, and Extended Master Secret must match (RFC 7627 §5.3): a session that used it cannot be resumed without it (`handshake_failure`), and a session that did not is answered with a full handshake.
- `Config.SessionTicketsDisabled bool` and `Config.SessionTicketLifetime time.Duration` (default 48 hours; the advertised lifetime is capped at 7 days).
- TLS 1.2 Extended Master Secret (RFC 7627). When the client offers `extended_master_secret`, the server echoes it and derives the master secret from the handshake transcript through ClientKeyExchange, so a man in the middle cannot synchronise two sessions to the same keys. Clients that do not offer it keep the classic derivation.
- TLS downgrade protection. A TLS 1.2 ServerHello ends its random value with the bytes `44 4F 57 4E 47 52 44 01` ("DOWNGRD" and 0x01) (RFC 8446 §4.1.3), so a TLS 1.3-capable client detects an attacker forcing TLS 1.2. A ClientHello carrying `TLS_FALLBACK_SCSV` from a client that does not offer TLS 1.3 is refused with `inappropriate_fallback` (RFC 7507).
- Client certificate authentication (mutual TLS) on TLS 1.3, TLS 1.2 and HTTP/3. `Config.TLSClientAuth` selects the policy: `NoClientCert` (default), `RequestClientCert`, `RequireAnyClientCert`, `VerifyClientCertIfGiven` or `RequireAndVerifyClientCert`, with the same meaning as `crypto/tls`. `Config.TLSClientCAs` is the pool used for verification (the system roots when nil). `CertConfig.ClientAuth` and `CertConfig.ClientCAs` override either setting for one certificate's host names. The server sends a CertificateRequest (TLS 1.3: after EncryptedExtensions, with `signature_algorithms`; TLS 1.2: ECDSA and RSA certificate types with an empty CA list), checks the client's CertificateVerify signature over the transcript, and verifies the chain for the `clientAuth` extended key usage. A missing certificate when one is required gets `certificate_required` on TLS 1.3 and `bad_certificate` on TLS 1.2; an untrusted issuer gets `unknown_ca`, an expired certificate `certificate_expired`, any other chain failure `bad_certificate`, and a CertificateVerify that does not verify `decrypt_error`. On HTTP/3 the same conditions close the connection with `CRYPTO_ERROR`. `Request.TLSPeerCertificates()` returns the client's certificate chain as sent (leaf first), or nil. Session tickets carry the client certificate: a resumed session gets it back after the chain is checked again against the current policy, and a ticket is not used when the policy now requires a certificate the session did not have, when client authentication has been turned off for a session that had one, or when the stored certificate has expired; those cases fall back to a full handshake. TLS 1.2 clients sign with ECDSA P-256 SHA-256, RSA-PSS SHA-256 or RSA PKCS#1 v1.5 SHA-256; TLS 1.3 clients additionally with ECDSA P-384/P-521, RSA-PSS SHA-384/512 and Ed25519.
- `Config.TLSClientAuth ClientAuthType`, `Config.TLSClientCAs *x509.CertPool`, `CertConfig.ClientAuth *ClientAuthType`, `CertConfig.ClientCAs *x509.CertPool`.
- OCSP stapling (RFC 6066 §8, RFC 8446 §4.4.2.1) on TLS 1.3, TLS 1.2 and HTTP/3. For a certificate whose leaf names an OCSP responder and whose chain includes the issuer, the server fetches the status in the background (HTTP POST, 10 second timeout, response capped at 16 KiB), refreshes it halfway between its `thisUpdate` and `nextUpdate`, and retries a failed fetch after 1 minute, doubling up to 1 hour. A response is used only if it is signed by the issuer (or by a responder certificate the issuer signed with the OCSP signing usage), reports the certificate as good, and has a `nextUpdate` in the future; a staple is no longer sent once its `nextUpdate` has passed. The staple is sent only to clients that ask for it with `status_request`: in the leaf's certificate entry on TLS 1.3 and HTTP/3, and as a CertificateStatus message with the `status_request` echo on TLS 1.2. Fetching never delays a handshake, and a failed fetch leaves the previous staple in place until it expires. Certificates without an OCSP URL and self-signed certificates are never fetched for. `Config.DisableOCSPStapling` turns the background fetch off. A staple can also be supplied by hand with `CertConfig.OCSPStapleFile` (a DER OCSP response; an invalid one fails start-up) or `(*CertEntry).SetOCSPStaple`; `(*CertEntry).OCSPStaple` returns the staple currently served.
- `Config.DisableOCSPStapling bool`, `CertConfig.OCSPStapleFile string`, `(*CertEntry).SetOCSPStaple(der []byte) error`, `(*CertEntry).OCSPStaple() []byte`.
- The reverse proxy sends `X-Forwarded-Proto` (`http` or `https`), `X-Forwarded-Host` and `Forwarded` (RFC 7239: `for=`, `proto=` and `host=`) to backends, in addition to `X-Forwarded-For`, on every proxy path (the epoll server's `AddProxyDomain`, `ProxyEngine.Handle` and WebSocket forwarding). `X-Forwarded-Host` and `host=` are sent only when the request's `Host` passes `ValidateHost`; an IPv6 client is written as `for="[2001:db8::1]"`, and a client address that is not an IP address as `for=unknown`. When the connection comes from a trusted proxy (`Config.TrustedProxies` or `RealIP`), the incoming `X-Forwarded-For` chain is kept and the proxy's address is appended; otherwise the value is the client's address alone.
- Upstream TLS trust per backend: `BackendConfig.RootCAs` (verify the backend against a private CA instead of the system roots), `BackendConfig.ServerName` (the name sent in SNI and checked against the backend's certificate, instead of the host in `Addr`) and `BackendConfig.ClientCert` (a client certificate for backends that require mutual TLS). They apply on every proxy path, to health checks and to WebSocket forwarding. The proxy's TLS client answers a CertificateRequest on TLS 1.3 and TLS 1.2 with the configured certificate and a CertificateVerify signed with ECDSA, RSA-PSS (RSA PKCS#1 v1.5 on TLS 1.2 when the backend does not accept PSS) or Ed25519, or with an empty certificate when none is configured. Backends with different trust settings never share pooled connections.
- JWT algorithms HS384, HS512, RS256, PS256, ES256 and EdDSA, in addition to HS256. The algorithm is pinned by the key's type: an HMAC `Secret` accepts only HS256/384/512, an `*rsa.PublicKey` only RS256 and PS256, an `*ecdsa.PublicKey` on P-256 only ES256, and an `ed25519.PublicKey` only EdDSA, so `alg: none` and HMAC-signed tokens checked against a public key are always refused. New `JWTConfig` fields: `Key` (a public key), `KeyFunc func(kid, alg string) (any, error)` (picks the key per token), `Algorithms` (narrows the accepted algorithms), `Audience` (the token's `aud` must contain one of them), `Issuer` (must equal `iss`), `Leeway` (clock skew allowed for `exp`, `nbf` and `iat`) and `AllowMissingExp`. `VerifyJWT(token, cfg)` checks a token outside the middleware and returns its claims or one of `ErrJWTMalformed`, `ErrJWTAlg`, `ErrJWTSignature`, `ErrJWTExpired`, `ErrJWTMissingExp`, `ErrJWTNotYetValid`, `ErrJWTAudience`, `ErrJWTIssuer`. Tokens longer than 64 KiB are refused.
- ACME Renewal Information (ARI, RFC 9773). When the CA's directory advertises `renewalInfo`, each certificate's suggested renewal window is fetched and the certificate is renewed at a random time inside it (at once if that time has already passed); the window is fetched again after the CA's `Retry-After` (between 1 minute and 24 hours, 6 hours when absent or on an error). Without ARI the certificate is renewed 30 days before it expires, as before. The renewal loop now wakes when the next renewal or ARI check is due instead of only every 6 hours.
- IPv6 backends. A backend address can be an IPv6 literal (`[2001:db8::7]:8080`, or `https://[::1]` with the default port), and a backend host name with no IPv4 address resolves through its AAAA record. IPv4 is still preferred: the A record is looked up first, and in `/etc/hosts` an IPv4 entry wins over an IPv6 one for the same name. IPv6 nameservers in `/etc/resolv.conf` are used. A TLS backend reached by IP address is verified against the IP addresses in its certificate.
- `Config.Logger *slog.Logger`: everything the server logs (start-up, certificate and ACME events, rejected connections, proxy health changes, recovered panics, the `Logger()` middleware and `Dbg` output) goes through it. Without it, records are written through the standard `log` package as `[LEVEL] message key=value …`, with empty values and values containing spaces, quotes, `=`, control characters or non-ASCII bytes quoted; `Debug` records are written only while `SetDebugFlag(true)` is set. Successful requests log nothing.
- `Config.OnPanic func(req *Request, recovered any, stack []byte)`: called after a handler panic is recovered, with the request (nil when the panic happened outside a request), the panic value and the goroutine's stack. Every recovered panic is also logged at `Error` level with its stack and, when there is a request, its method and path. This covers the `Recovery()` and `Timeout()` middleware, HTTP/1, HTTP/2 and HTTP/3 handlers on every backend, WebSocket handlers, and the server's internal goroutines. What the client receives is unchanged (`500 Internal Server Error` where a response can still be sent).
- `MetricsHandler()`: a handler that serves `Stats` in the Prometheus text format (`text/plain; version=0.0.4; charset=utf-8`): the gauge `alos_http_active_connections` and the counters `alos_http_connections_total`, `alos_http_requests_total`, `alos_http_requests_blocked_total`, `alos_http_h1_rejected_total`, `alos_http_bytes_received_total`, `alos_http_bytes_sent_total`, `alos_http_h1_connections_total`, `alos_http_h2_connections_total` and `alos_http_h3_connections_total`. Mount it on a route of your choice (`srv.Router.GET("/metrics", core.MetricsHandler())`); it does not allocate when the response is reused.
- Brotli response compression (`Content-Encoding: br`) in `Compress`, the built-in `Config.EnableCompress` path and the response cache. Brotli writers are pooled per level. `CompressConfig.BrotliLevel` and `Config.CompressBrotliLevel` set the level (1–11, default 4; anything else uses 4). `CacheConfig.Brotli` stores a brotli copy of each compressible entry next to the gzip one (`CacheConfig.BrotliLevel`, default 4; the `GzipMinBytes` threshold applies to both), and each hit serves the best copy the client accepts without allocating.
- `CSRFConfig.TrustedOrigins []string`: extra origins (`scheme://host[:port]`, compared case-insensitively, default ports ignored) allowed to send unsafe requests through `CSRF`'s origin checks. `CSRF` panics on an entry that is not of that form.
- `SecurityHeadersConfig.ContentSecurityPolicy`, `PermissionsPolicy`, `CrossOriginOpenerPolicy`, `CrossOriginResourcePolicy` and `CrossOriginEmbedderPolicy`: each non-empty value is sent as the matching header. The header list is built once, so the middleware still adds no allocations per response.
- WebSocket subprotocols and compression. `UpgradeWebSocketWith(req, resp, WSUpgradeOptions)` and `ServeWebSocketWith(req, resp, WSUpgradeOptions, fn)` take `Subprotocols` (the server's protocols in order of preference; the first one the client also offered is selected, compared exactly, and echoed in `Sec-WebSocket-Protocol`; no header is sent when there is no overlap), `Compression`, `CompressionLevel` (1–9, default 1) and `MaxMessageSize`. `(*WSConn).Subprotocol()` returns the selected protocol. `UpgradeWebSocket` and `ServeWebSocket` behave as before.
- permessage-deflate (RFC 7692), when `WSUpgradeOptions.Compression` is set and the client offers it. The server answers `permessage-deflate; server_no_context_takeover; client_no_context_takeover`, so every message is compressed and decompressed on its own and a connection keeps no 32 KiB compression window between messages. An offer with an unknown, repeated or malformed parameter, or with `server_max_window_bits` below 15, is declined (the next offer in the header is considered). Text and binary messages of 64 bytes or more are sent compressed; control frames never are. A message is decompressed only up to `MaxMessageSize`: a compressed message that inflates past it (a decompression bomb) closes the connection with 1009 as soon as the limit is crossed, and data that does not decompress closes it with 1007. Compressing secrets alongside attacker-controlled data over TLS can leak them through message sizes (CRIME-style), so compression is off unless enabled.
- WebSocket over HTTP/2 (RFC 8441) on the epoll server, with TLS and h2c. The server advertises `SETTINGS_ENABLE_CONNECT_PROTOCOL` (`0x8`) = 1, and an extended `CONNECT` with `:protocol: websocket` (which must also carry `:scheme`, `:path` and `:authority`) is routed to the `GET` handler of its path, so existing `ServeWebSocket` / `UpgradeWebSocket` routes accept it unchanged. The handshake answers `:status 200` (no `Sec-WebSocket-Accept`; `Sec-WebSocket-Version: 13` is still required, otherwise `426`), with the same `Origin` check, subprotocol selection and permessage-deflate negotiation as HTTP/1.1. WebSocket frames travel in the stream's DATA frames under HTTP/2 flow control; closing the `WSConn` ends the stream with `END_STREAM`, and a client `RST_STREAM` or a closed connection fails its reads and writes. The stream stays open after the handler returns until the `WSConn` is closed, so handlers that upgrade and hand the connection to their own goroutine keep working; `MaxBodySize` and `MaxWriteSize` do not apply to the stream's total traffic (`MaxMessageSize` limits each message). `const H2SettingEnableConnectProtocol uint16 = 0x8`. `:protocol` is refused on the non-epoll HTTP/2 server, which does not advertise the setting.
- `WrapHTTPHandler(h http.Handler) HandlerFunc` runs a standard `net/http` handler (for example `http.FileServer`, `http.StripPrefix` or `net/http/pprof`) as a route. The handler gets an `*http.Request` with the method, target (`URL`, `RequestURI`), `Host`, `RemoteAddr`, protocol (`HTTP/2.0` for HTTP/2), headers in canonical form, body (streamed when the server streams request bodies), `ContentLength`, `TLS` (version and client certificates) and the request's `Context()`. Status, headers and every `Write` are kept; `Content-Type` is sniffed from the first 512 bytes when the handler did not set it (a `nil` `Content-Type` entry turns sniffing off, as in `net/http`); `Content-Length` and hop-by-hop headers set by the handler are dropped because the server frames the response itself; CR and LF are removed from header values. `http.Flusher` switches the response to streaming and sends what has been written so far. `http.Hijacker` is implemented but always returns an error. Each request allocates the `net/http` request and header maps, unlike native handlers.
- Server-Sent Events: `(*SSEWriter).SendComment(text)` writes a comment block (`: text`), `(*SSEWriter).StartHeartbeat(interval)` writes `: ping` every `interval` from its own goroutine until the returned `stop` function is called (`stop` waits for the goroutine to finish, so nothing is written after it returns; a non-positive interval starts nothing), and `(*Request).LastEventID()` returns the `Last-Event-ID` header a reconnecting client sends. `SSEWriter` methods are now safe to call from several goroutines; each event is written whole.
- `Cookie.Partitioned` adds the `Partitioned` attribute (CHIPS: the browser keys the cookie to the top-level site it was set under) and always adds `Secure`, which browsers require for partitioned cookies.
- `Stats.Snapshot()` returns a `StatsSnapshot`, a plain struct with every counter loaded once. `Stats.H3Conns` counts QUIC connections that completed the handshake.
- Passive outlier ejection for proxied domains, on every proxy path. A backend that fails five requests in a row (a connection, DNS or protocol error, a timeout, or a `5xx` response) receives no traffic for 30 seconds; any other response resets the count. Each further ejection doubles the time up to 5 minutes, and a backend that stays in service for 5 minutes after an ejection ends starts again from 30 seconds. At most half of a domain's backends are ejected at once, so a domain with a single backend never loses it. Ejected backends are skipped by every load balancer and by retries. `DomainConfig.Outlier` (`OutlierConfig{Disabled, ConsecutiveFailures, BaseEject, MaxEject, MaxEjectPercent}`) changes the thresholds or turns ejection off.

### Changed

- HTTP/1 header parsing uses a fused AVX2 scanner (line end, illegal bytes and header-name validation in one pass; SWAR fallback without AVX2). With strict validation enabled, parsing is still faster than before: typical request −7%, browser request −2%, POST request −1%.
- Response cache hits no longer allocate (−29% time per hit, 1 → 0 allocations).
- Serialising a proxied request costs 1% less than before although it now writes three more headers (`X-Forwarded-Proto`, `X-Forwarded-Host`, `Forwarded`): the client address is split and checked in one pass, header names are compared without a preliminary full-string comparison, short values are checked for CR and LF 8 bytes at a time, and the `Upgrade` header is picked up during the header copy instead of in a second scan.
- HTTP/2 request header decoding is 6.6% faster: header values are checked for NUL, CR and LF 8 bytes at a time (up to 32 bytes) or with the vectorised byte search (longer values) instead of one table lookup per byte.
- HTTP/3: once a client address is validated, packets no longer update the anti-amplification byte counters (two atomic additions per packet before), and the per-packet path check reads a cached address instead of taking a lock. With all of this release's HTTP/3 additions in place, the HTTP/3 benchmark (64 connections × 8 streams) serves the same or more requests per second than before (root +0.2%, routed +1.7%) and the server spends about 4% fewer CPU cycles per request.
- TLS 1.3 handshakes with X25519 do two scalar multiplications instead of three. The server's ephemeral key is kept as a `crypto/ecdh` private key, so computing the shared secret no longer recomputes its public key. The server's work to answer a ClientHello dropped from 222 µs to 173 µs on one core (−22%) and from 175 µs to 120 µs with four cores (−31%); the X25519MLKEM768 hybrid gets the same saving.
- Router method lookup compares the whole method name in one step instead of a two-letter prefix followed by a string comparison: static-route lookup takes 5% fewer instructions and 7% fewer cycles than before exact method matching was introduced.
- ACME retries back off instead of stopping. A failed certificate order is retried after 5 minutes, then 10, 20 and so on up to 24 hours (±10% jitter), indefinitely, and a rate-limit error waits for the CA's `Retry-After`; previously three attempts 5 minutes apart were followed by a 24-hour pause. A failed renewal follows the same backoff rather than retrying at every check. Domains are obtained in parallel at start-up, so one failing domain no longer delays the others.
- A malformed HTTP/2 request on the epoll server (missing `:method`, `:scheme` or `:path`, a `CONNECT` that carries `:scheme` or `:path`, `:protocol` on anything but `CONNECT`) is now reset with `RST_STREAM(PROTOCOL_ERROR)` (RFC 9113 §8.1.1) and the connection keeps serving its other streams. It used to close the whole connection with `GOAWAY(COMPRESSION_ERROR)`. Errors found while decoding a header block (an invalid field name or value, a connection-specific field, a repeated or unknown pseudo-header) still close the connection, because decoding stops midway and the HPACK table can no longer be trusted.
- WebSocket payload unmasking uses AVX2 when available (32 bytes per instruction, 128 per loop iteration): on the test server, unmasking a 125-byte frame takes 13 ns instead of 20, 1 KiB 15 ns instead of 142, 16 KiB 141 ns instead of 2.1 µs. Frames under 32 bytes take about 1 ns longer (one more function call). Other CPUs keep the 8-bytes-per-step loop.
- Formatting a Server-Sent Event no longer allocates: the event is built in a pooled buffer instead of a `strings.Builder` whose result was copied into a new byte slice.
- A WebSocket message or frame larger than `MaxMessageSize` now closes the connection with status 1009 (message too big) instead of a close frame without a status.
- `Accept-Encoding` is negotiated by quality value (RFC 9110 §12.5.3) everywhere a response is compressed (`Compress`, `EnableCompress`, the response cache and the proxy cache): the coding with the highest `q` wins, ties go to `br`, then `gzip`, then `deflate`; `*` covers codings not listed; `x-gzip` counts as `gzip`; a malformed `q` makes that coding unacceptable. Previously any non-zero `q` counted as 1, so `gzip;q=0.1, deflate` got gzip, and brotli was never chosen. Compressed and compressible responses now carry `Vary: Accept-Encoding` also when they are sent uncompressed (the client accepted none of the codings, or compression did not shrink the body), so shared caches keep the variants apart; the header is not added again when the response's `Vary` already covers `Accept-Encoding`. Parsing a typical browser header (`gzip, deflate, br, zstd`) costs the same as before; headers with explicit `q` values cost about 20 ns more, as their values are now actually read.
- A backend IPv4 address written with leading zeros (`010.0.0.1`) is no longer read as an IP address, since it is ambiguous between decimal and octal; it is looked up as a host name instead.
- Multipart parsing is zero-copy. A measured bake-off against a memory-plus-spill-to-disk design found zero-copy better or equal on every metric at every size (1 KiB form to 64 MiB file, and 1000 parts): 2.2–16× faster, 760 B instead of 74 MiB allocated per 64 MiB upload, peak RSS 12 KiB instead of 74 MiB, and with 64 concurrent uploads the same throughput at 64 KiB (within 1%) and 10% more at 1 MiB. The spill design was not kept.
- TLS 1.3 record sealing and opening keep the nonce and additional-data scratch in the connection's cipher state instead of taking it from a `sync.Pool` per record: sealing a 64-byte record takes 7.7% less time, 512 bytes 5.0%; opening 8.5% and 5.4%. A TLS 1.3 HTTP/1 server spends about 3% fewer instructions per request.
- HTTP/1 handlers that run off the event loop no longer allocate per request (2 → 0 allocations): each connection keeps one handler function value, and finished requests return to the event loop through a lock-free list instead of a closure sent over a channel. Sixteen pipelined requests take 11.9% less time, a single request 5.2% less; routed HTTP/1 requests per second rose 3.3% in plain text and 2.8% over TLS.
- HTTP/1 responses over TLS with a body of at least 16 KiB (TLS 1.3) or 32 KiB (TLS 1.2) are sealed straight from the response body instead of being copied into a plaintext buffer first. The records on the wire are byte-for-byte the same. TLS 1.3: 16 KiB −6.3%, 64 KiB −12.2%; TLS 1.2: 32 KiB −3.9%, 64 KiB −10.0%. Bodies over 512 KiB already took the streaming path and are unchanged.
- Request strings that point into the read buffer are moved out of it with one copy of the request head and a pointer rebase, instead of one copy per field; the connection's own remote address and the built-in method and protocol strings are no longer copied at all. Parsing plus copying a curl-sized request takes 13.8% less time, a typical request 18.9% less, a browser request 15.8% less.

### Fixed

- HTTP/2: a stream whose request body gets no bytes for `ReadTimeout` while the peer may send, also while its handler streams the body, gets `RST_STREAM(CANCEL)`; PING and other control frames do not extend it. A response, buffered or streamed, that waits for the peer's flow-control window for `WriteTimeout` without sent DATA gets `RST_STREAM(CANCEL)`. Only that stream ends; the connection and other streams continue. WebSocket tunnels keep `WSReadTimeout` as their idle limit.
- HTTP/2: a HEADERS frame (trailers) that the peer sent on a stream before it saw the server's RST_STREAM is ignored instead of closing the connection with GOAWAY(PROTOCOL_ERROR).
- HTTP/2: after the peer half-closes the connection and all its input was read, body readers get `ErrBodyStreamAborted`, streams that still wait for body bytes or for a flow-control window are dropped, the remaining in-flight responses are sent, and the connection then closes.
- HTTP/1: a streamed request body is charged to `MaxInFlightBodyBytes`. When the budget has no room the request gets `503` and the connection closes; an over-size chunked body gets `413`.
- `BodyLimit` caps streamed request bodies: `Read` returns `ErrBodyTooLarge` past the limit and the response becomes `413`.
- A stream writer kept by a handler after it returns can no longer write into a later response; its calls return `ErrStreamClosed`.
- HTTP/1: a streamed or sendfile body that fails after the handler returned closes the connection instead of keeping it alive after a short body.
- Dispatched proxy responses use transfer encoding when deciding whether to stream and enforce the upstream response-body limit when buffering. Declined-upgrade responses also enforce the buffered-body limit; oversized responses are rejected before their contents are exposed.
- HTTP/1 methods are matched exactly. Previously any 4-byte method starting with `H` was treated as `HEAD`, any 6-byte method starting with `D` as `DELETE`, any 5-byte method starting with `PA` as `PATCH`, and any 7-byte method starting with `O` as `OPTIONS`.
- An HTTP/1 request line without spaces is rejected with 400 instead of leaving the connection waiting for more input.
- Empty lines (CRLF) sent before an HTTP/1 request line are ignored (RFC 9112 §2.2).
- `sanitizeRequestPath` now truncates at the first NUL, CR or LF. Previously a path containing both a NUL and a CR kept the CR.
- The HTTP-to-HTTPS redirect listener keeps accepting after transient `Accept` errors (with a 5ms–1s backoff) instead of stopping on any error that was not reported as temporary.
- Upstream (proxy and client) TLS 1.2 with certificate verification, the default, never completed: the Certificate message was parsed in the TLS 1.3 layout.
- Upstream TLS 1.2 ServerKeyExchange signatures: SHA-384 and SHA-512 schemes were verified with SHA-256, the key type was not checked against the scheme, and unknown schemes fell back to SHA-256 instead of failing. The client now offers ten signature schemes (ECDSA P-256/P-384/P-521, RSA-PSS and PKCS#1 v1.5 with SHA-256/384/512, Ed25519).
- The proxy path used by `ProxyEngine.Handle` ignored `DomainConfig.ConnectTimeout` and `ReadTimeout`.
- A fatal TLS alert is now delivered before the connection closes. The server half-closes the connection after the alert and discards what the client is still sending (at most 16 MiB for at most one second, the same rule as an HTTP/1 close) instead of closing with unread data, which made the kernel send a TCP reset that could reach the client before the alert. A second ChangeCipherSpec from a TLS 1.2 client now gets `unexpected_message`; it used to be ignored.
- The TLS server sends `close_notify` (RFC 8446 §6.1, RFC 5246 §7.2.1) before it closes a connection after a response (`Connection: close`, HTTP/1.0, an error response that ends the connection, an HTTP/2 connection close), and then closes the same way as after a fatal alert. Previously it closed the TCP connection without one, which clients built on OpenSSL 3 report as an unexpected EOF.
- With client authentication configured (`Config.TLSClientAuth` or any `CertConfig.ClientAuth` other than `NoClientCert`), the `GET /` handler runs for every request. It used to run once at start-up with its response replayed for every request, so `Request.TLSPeerCertificates()` always returned nil there.
- `Stats.BytesIn` and `Stats.BytesOut` were never updated and always read 0. They now count the bytes received from and sent to clients on every protocol (HTTP/1.1, HTTP/2, TLS records, `sendfile`, and HTTP/3 datagrams). The epoll workers keep their own totals and add them to `Stats` once per event batch, so a value can lag by one batch.
- The WebSocket server sent two close frames when it closed with a status (a protocol error, invalid UTF-8, an oversized message) or answered a client's close: one with the status and an empty one after it. RFC 6455 §5.5.1 forbids sending anything after a close frame. It now sends exactly one.
- A fragmented WebSocket message whose first fragment was empty was rejected as a protocol error when its continuation frame arrived.
- The response cache and the proxy cache sent the gzip copy to clients that refused gzip with `q=0.0` or `q=0.000` (only a bare `q=0` was recognised), and their uncompressed responses for an entry that also had a gzip copy lacked `Vary: Accept-Encoding`.
- `Stats.TotalConns` counted only HTTP/3 connections; TCP connections accepted by the epoll server are now counted too. HTTP/3 requests now count towards `Stats.TotalReqs` and `Stats.RawReqs`, as HTTP/1 and HTTP/2 requests already did.
- Upstream timeouts on the epoll server were checked only once per second, so a short `ReadTimeout` could fire up to a second late.
- A failed proxy attempt decremented the backend's active-connection count twice (and a DNS failure decremented it without an increment), skewing least-connections balancing.
- `Request.FormValue` returned nothing for `multipart/form-data` bodies unless `FormFile` had been called first.
- A `Range` request to `SendFile` or `Static` previously received the whole file with `200`, and a file that shrank while being sent ended the response early with a short body; it now fails the response.
- `Shutdown` never closed HTTP/3 connections: the QUIC listeners stopped and the connections' timers stopped with them, so `Shutdown` always ran until its context expired while any HTTP/3 connection was open. Connections now drain as described above, and the UDP listeners stay open until the last one has closed.
- A QUIC `STREAM` frame for a request that had already been answered created the stream again and ran the handler a second time.
- QUIC packets with very small payloads could not be decrypted by the client because the header-protection sample ran past the end of the packet; they are now padded (RFC 9001 §5.4.2).
- An HTTP/3 request beyond the concurrent-request limit was silently dropped, leaving the client waiting; it is now refused with `H3_REQUEST_REJECTED`.
- QUIC frames of an unknown type, and malformed frames, now close the connection with `FRAME_ENCODING_ERROR`; previously the error was logged and the rest of the packet ignored.
- TLS 1.2 `renegotiation_info` (RFC 5746) is sent only when the client signalled support (the extension or `TLS_EMPTY_RENEGOTIATION_INFO_SCSV`); it was previously sent to every client, which RFC 5246 §7.4.1.4 forbids. An initial ClientHello whose `renegotiation_info` is not empty, and any renegotiation attempt after the handshake, are refused with `handshake_failure` and the connection is closed.
- A streamed request body (epoll HTTP/1) whose client disconnected while the server was holding back input for a slow handler could leave the handler blocked in `Read` until the read timeout, because the disconnect was not seen again once reading resumed. The handler now gets `ErrBodyStreamAborted` as soon as the remaining input is used up, and a client that sends its whole body and then half-closes still gets its response.
- A QUIC ServerHello larger than one packet's crypto budget is split across several padded Initial packets instead of being sent in one oversized datagram that clients drop. Only the X25519MLKEM768 ServerHello (1,120-byte key share) is that large.

### Security

- Chunked request bodies on the epoll HTTP/1 path are validated by the same strict decoder as the streaming path. Previously the completeness check skipped any two bytes after chunk data and the decoder skipped to the next line feed, so bodies such as `5\r\nhelloXX\r\n0\r\n\r\n` could be framed differently than by a strict front-end proxy.
- Go toolchain raised to 1.26.9, which fixes 14 standard-library vulnerabilities reachable from this module (net/http, crypto/tls, net/url, encoding/asn1, net/textproto). `golang.org/x/crypto` raised to v0.58.0 and `golang.org/x/sys` to v0.49.0.
- Strict HTTP/1 parsing removes request-smuggling and header-injection ambiguities (whitespace before colons, obsolete folding, bare LF, duplicate `Host`).
- The response cache could serve one user's personalised response to another user (cookie or bearer-token sessions).
- A misconfigured `RealIP` trusted `X-Forwarded-For` from every client, allowing IP spoofing.
- Non-idempotent proxied requests (for example a payment `POST`) could be executed twice when the first backend failed after receiving the request.
- The HTTP/1 fast path for `GET /` requests skipped the strict header checks. It now applies them, and is still faster than before: requests up to 96 bytes are validated in a single pass that also finds the end of the header block, longer ones by an AVX2 block indexer (64 bytes per step) after checking whether the buffer ends with the header terminator. Measured on the parser in isolation, a wrk-shaped request takes 26 ns instead of 51 (−48%), a three-header curl-shaped request 59 ns instead of 62 (−6%) and a browser-shaped request 173 ns instead of 193 (−10%).
- `Router.Lookup` ran a route's handler for methods that only shared the first two letters with the registered method.
- Server-Sent Events data split lines only at LF, but the event-stream format also ends a line at a lone CR. Data containing `\r` (for example `x\rid: 99` or `x\revent: admin`) therefore injected `id:` and `event:` fields of the sender's choosing into the stream. Data and comments are now split at CR, LF and CRLF, each piece written as its own `data:` (or `:`) line; `id` and `event` values already had CR and LF removed.
- `Cookie.String` (and so `Response.SetCookie`) removed only CR, LF and NUL from the name, value, path and domain, so a value taken from user input such as `x; Domain=evil.example; Max-Age=999999` added attributes of the attacker's choosing. `;` is now removed from those four fields too.
- `SecurityHeaders` copied `XFrameOptions` and `ReferrerPolicy` into responses unchecked, so a value containing CR or LF (for example one read from a config file) could add arbitrary response headers. CR, LF and NUL are now removed from every configured value, and a value that is empty afterwards is not sent.
- QUIC stream limits are enforced: a client opening a stream beyond the advertised `MAX_STREAMS` is closed with `STREAM_LIMIT_ERROR`, a `STREAM` frame on a stream the client cannot send on with `STREAM_STATE_ERROR`, and stream credit is granted back in batches as requests finish (256 concurrent request streams, 16 unidirectional). Previously any stream ID was accepted.
- QUIC address validation (Retry) stops spoofed-source Initial floods from creating connection state, and the server never sends more than three times the bytes it received to an unvalidated address, including on a migrated path.
- The epoll server's reverse proxy did not check the host name of a TLS backend's certificate: any certificate from a trusted CA was accepted, whatever name it was issued for. It also sent an empty `server_name`, which backends that insist on a well-formed ClientHello reject. The certificate is now verified for the backend's host (or `BackendConfig.ServerName`). SNI is sent only for host names, never for an IP address (RFC 6066 §3).
- The reverse proxy relayed a client's own `X-Forwarded-Proto` and `X-Forwarded-Host` to backends unchanged, so a client could claim HTTPS or another host name. Both are now removed and replaced with the proxy's own values, like `X-Forwarded-For`, `X-Real-IP` and `Forwarded` already were.
- The reverse proxy removes the headers a client names in `Connection` (RFC 9110 §7.6.1), so `Connection: X-Secret` with `X-Secret: 1` no longer reaches the backend. `ProxyEngine.Handle` also relayed `Connection`, `Upgrade` and `Proxy-Connection` themselves; it now drops every hop-by-hop header, as the other proxy paths already did.

### Removed

- The precomputed `GET /` response on HTTP/1 and HTTP/2. The server ran the `/` handler once at startup and sent its bytes for each later `GET /`. The `/` handler now runs for each request like every other route, and HTTP/2 `GET /` responses obey the peer's flow-control window.
- Unused `createQUICListeners` on linux/amd64 and unused `prepareAcceptedFD` on non-linux builds.
- `Server.ServeH2` and `Server.ServeH2Plain`, the goroutine-per-connection HTTP/2 servers that the epoll server replaced; no listener called them. With them go the types and helpers only they used: `H2Conn`, `H2StreamWriter`, `Server.NewH2StreamWriter`, `WriteRequest`, `H2StreamWriterPool`, `H2FrameBufPool` and `ErrChanPool`. Since nothing called them, how connections are served does not change.
